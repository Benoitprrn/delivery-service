## 1. Objectif
Le commerçant marque une livraison « Paiement à la livraison » + montant (centimes). À la remise, le livreur saisit le code client puis encaisse par Stripe Terminal (lecteur physique en production ; lecteur simulé officiel en développement) dans l'app Locadely. Le backend seul décide `COMPLETED`.

## 2. Architecture retenue (sous réserve du gate G1)
- **Un seul Account v2 par restaurant** (`merchant_payment_profiles.stripe_account_id`) : configuration `customer` (SEPA, existante) + ajout `merchant` (card_payments) sur le même `acct_`.
- **Direct Charge** (préférence POC) : PaymentIntent, Location et ConnectionToken sur le compte du restaurant (header `Stripe-Account`). Restaurant supporte frais, remboursements, litiges. Locadely : 0 commission.
- **Nouveau module API `cash-on-delivery`** (public.ts) ; `payments` (SEPA) inchangé hors extension webhook. `orders` ne garde qu'un snapshot COD immuable + une garde DB.
- **Reader abstraction** côté mobile (`ReaderAdapter`) ; backend ne connaît que `reader_type` + `location`.
- **Parcours de livraison COD (code AVANT paiement, capture manuelle)** :
  1. `POST /orders/:id/delivery-completion-sessions` {expectedVersion, deliveryCode} → serveur vérifie livreur/COLLECTED/version/code (compteur d'essais existant), persiste `code_verified`. Non-COD : finalise `COMPLETED` immédiatement (règles actuelles).
  2. Même réponse COD : `paymentId`, `amountCents`, `currency`, `paymentIntentClientSecret` — PI créé serveur (hors transaction PG), `capture_method=manual`, `payment_method_types=['card_present']`, compte/montant/devise dérivés de la commande, clé d'idempotence par tentative.
  3. Mobile : `POST /orders/:id/terminal/connection-token` (aucun accountId client) → découverte + connexion du lecteur via `ReaderAdapter` (famille de lecteur, `locationId` du restaurant) → `retrievePaymentIntent` → `collectPaymentMethod` → `confirmPaymentIntent` (statut `requires_capture`).
  4. `POST …/finalize` {paymentId} : serveur RELIT le PI chez Stripe, vérifie compte/montant/devise/metadata/statut, CAPTURE (hors transaction), puis 1 transaction : paiement `succeeded` + session `completed` + `orders COMPLETED` + `order_events` + `outbox_event`. Décrément capacité après transition réelle.
  5. Crash après capture : commande `COLLECTED` + paiement capturé → `GET …/delivery-completion` reprend et finalise sans réencaisser. Webhook `payment_intent.succeeded` = réconciliation, jamais source primaire.
  6. Échec après autorisation : `cancel` du PI (libère la carte). Autorisation non capturée expire à 2 jours (Stripe) → worker de réconciliation.
- Garde DB défense en profondeur : `CHECK (status <> 'COMPLETED' OR cash_on_delivery_required = false OR cash_on_delivery_collected_at IS NOT NULL)`.
- Signature/photo interdites si COD (elles contournent le code). `returnOrder` (client absent) interdit si PI autorisé/capturé (annuler d'abord ; capturé → procédure support).
- Pas de nouvel état `orders.status` : substate persisté dans `order_delivery_completion_sessions` (ADR 0001 à amender).
